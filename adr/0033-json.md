# ADR-0033: `json` type, parse and print

Status: Proposed
Date: 2026-11-17

## Context
T-028 (v0.2) asks for JSON parse/print, with a Proposed ADR first. SPEC §4
lists a "JSON value type" for v0.2 and nothing else. Sum types (T-029) do not
exist yet, so a JSON value cannot be a user-visible variant type. Constraints:
deterministic output, interpreter and native backend byte-identical (T-020),
few tokens in `llms.txt` (ADR-0026 budget).

Options (score 1-10):
- An opaque `json` type with a generic constructor and typed `opt`
  accessors, objects exposed as `dict str json` (ADR-0032). Reuses `opt`,
  `list`, `dict`; no new syntax. **8**
- Decode straight into records (`jparse T s`): needs reflection over record
  types, nested lists of records, missing-field rules; much larger. **5**
- Wait for sum types and model JSON as a sum: blocks T-028 on T-029 and still
  needs parse/print. **4**

## Decision
- Type `json` (arity 0; lexicon type concept `json`). Not primitive, not
  comparable with `==`/`!=`, not a dict key; `show` accepts it (below).
- A JSON value is one of: null, bool, integer (`i64`), number (`f64`),
  string, list of `json`, object (`dict str json`, keys ascending by bytes).
- Builtins (pure, no capability):
  - `json x` -> `json`, where `x` is `unit` (null), `bool`, `i64`, `f64`,
    `str`, `json` (returned as is), `list json` or `dict str json` (else
    T004, expected `jsonable`). A NaN or infinite `f64` becomes null. The
    type name doubles as the constructor, like record types.
  - Nesting depth (lists/objects; a scalar is 0, `[]` is 1) is at most 256
    for every JSON value: `json` on a list/dict whose result would be deeper
    traps R005 in both engines (`json` is the first recursive type; without
    the limit deep values overflowed the interpreter's stack and diverged
    from native). Each value stores its depth, so the check is O(children).
  - `jparse s` -> `res json str`;
  - `jbool j` -> `opt bool`; `jint j` -> `opt i64` (integers only);
    `jnum j` -> `opt f64` (integers converted); `jstr j` -> `opt str`;
    `jlist j` -> `opt list json`; `jdict j` -> `opt dict str json`.
    Each is `none` when `j` holds another kind. Null is tested with
    `== show j "null"`.
- `show j` prints compact JSON: no whitespace; object keys ascending; integers
  in decimal; numbers as `show` prints `f64` (`1.0`, `1e20`, `-0.0`); strings
  quoted with `\"`, `\\`, `\b \f \n \r \t`, other bytes below 0x20 as `\u00xx`
  (lowercase hex), everything else (including non-ASCII UTF-8) as is.
- `jparse` accepts RFC 8259 JSON text:
  - whitespace is space, tab, LF, CR;
  - a number without fraction or exponent that fits `i64` is an integer,
    any other number is an `f64` (correctly rounded); a number that rounds to
    infinity is an error;
  - `\uXXXX` escapes decode to UTF-8; surrogate pairs combine; a lone
    surrogate is an error;
  - nesting deeper than 256 arrays/objects is an error;
  - a duplicate object key is an error (no silent "last wins").
- `jparse` errors are `err "json: <reason> at byte <n>"`, `n` the 0-based
  byte offset. Reasons and offsets:
  - `unexpected end` at the input length;
  - `unexpected byte` at the offending byte (also raw control bytes in
    strings, trailing data, bad literals such as `tru`);
  - `bad number` at the number's first byte;
  - `bad escape` at the escape's backslash (the first one of a pair), also
    for a `\u` escape truncated by the end of input;
  - `duplicate key` at the opening quote of the repeated key with the
    smallest offset, reported only once its object parsed otherwise (an
    object's members are sorted once when it closes, so parsing is
    O(n log n) in its size);
  - `too deep` at the 257th opening bracket.
- Representation: both engines wrap a plain value with its depth
  (interpreter `Value::Json(Rc<Value>, u32)`, Tlön tag `AL_JSON` pointing to
  an `AlJson`), so `jlist`/`jdict` are O(1) and `json` on a list/dict is
  O(children).

## Consequences
- Agents read JSON with `try jparse s` and `else`/`has` on the accessors,
  e.g. `else jint else get else jdict j dict str json "n" json 0 0`;
  verbose, to be revisited with sum types and `match` (T-029).
- Key order of the input is not preserved; output is canonical, so
  `show try jparse t` normalizes JSON text.
- `json`, `jparse`, `jbool`, `jint`, `jnum`, `jstr`, `jlist`, `jdict` become
  reserved names (T005).
- `show` on JSON is the only way to get its text; a `json` inside a failed
  example's `expected`/`found` (E002) shows as that text.
